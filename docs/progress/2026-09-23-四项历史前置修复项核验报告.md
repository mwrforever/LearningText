> **修订说明**：在**用户真实库副本**上按四步复现流程逐步对账（树中每行 id 逐个 `getNode` 验活 + 点击/展开/重命名/建子级逐项驱动）后，仍未复现「目录完全无法操作」——新目录可选中可操作。判定为呈现层误判：旧 schema 下同名写操作次次以失败 toast 收场（观感为「这个目录用不了」），叠加行操作入口「⋯」常态透明仅悬停显形（看不到操作键）。两项分别由 v3 迁移与入口可见化处置（设计系统 §十三）。以下原文保留。

**核验路径**（真实用户路径复刻用户描述的动作序列，全部通过）：

1. 建目录 `回收再建`（含子文件）→ 树行「⋯」菜单 → 删除（入回收站）。

## ② HTML 渲染「灰色遮罩层」（定位真因并修复）

### 步骤一：证伪「存在覆盖层」

画布区 16 点 `elementsFromPoint` 网格采样（4×4），最上层元素**恒为 `IFRAME`**——不存在任何覆盖文档的应用层元素（若有覆盖层，即便 `pointer-events-none` 也会出现在命中链首）。故现象不在应用 DOM 层。

### 步骤二：真因取证（单变量实验）

先量出事实：打开的透明底 HTML 文档（`<html><body><h1>Hello</h1></body></html>`）文档区主色 = **应用底色**——亮色 `248,250,252`（`--background #f8fafc`）、暗色 `15,23,42`（`#0f172a`）；文档内根元素背景实测 `rgba(0, 0, 0, 0)`（透明）。

再做单变量实验（候选位置逐一改醒目色，**每次改动后等待 400ms 重绘再复采**——首轮无等待实测因合成器缓存给出自相矛盾读数，加等待后读数自洽且可逐次还原）：

| 改动位置 | 文档区主色 |
| --- | --- |
| iframe 元素 `background:#ff0000` | `255,0,0` |
| `.lt-html-canvas` 容器 `background:#00ff00` | `0,255,0` |
| `section.lt-canvas` `background:#0000ff` | `0,0,255` |
| 文档 `html` `background:#ffff00` | `255,255,0` |
| 逐次还原后基线复采 | 均回到 `248,250,252` |

**结论**：Chromium 中子文档根元素背景为 `transparent` 时其画布对嵌入者透明；文档未自设 `background` 时，最近的应用底色即透过文档显示——观感即用户所述「莫名其妙的灰色遮罩层」（亮色为浅灰蒙面、暗色为深灰蒙面，且「有时」出现正对应「文档是否自带背景」）。

### 步骤三：修复与复核

**修复**：`.lt-canvas-frame` 承载 `bg-white`（`src/renderer/src/features/canvas/HtmlCanvas.tsx`）。浏览器对顶层文档恒以白色为画布基底，白底即浏览器默认画布（保真度只增不减）；落 iframe 元素而非文档内——用户文档与保存序列化零污染，「不注入 UA 样式」的保真红线不破。

| 状态 | 亮色主题文档区主色 | 暗色主题文档区主色 | 文档自带背景（紫底反证） |
| --- | --- | --- | --- |
| 修复前 | `248,250,252` | `15,23,42` | — |
| 修复后 | `255,255,255` | `255,255,255` | `128,0,128`（基底不覆盖文档自身样式） |

**规则生成核证**（Tailwind v4 类串能力必须对构建产物 grep，M8 教训 ①）：`dist/renderer/assets/*.css` 命中 `.bg-white{background-color:var(--color-white)}` + `--color-white:#fff`。

### 已知边界（不在本修复范围）

CSP `default-src 'self'` 会拦掉文档引用的外链样式表（B.5-3 安全红线不可放宽），此类文档在应用内为「未套样式 + 白底」、在浏览器内为「套样式」——样式缺失是安全基线的既定代价，本修复保证「基底与浏览器一致」，不承诺「外链资源可用」。
