# 旧库 schema 缺陷（回收站不让名）修复批次报告（2026-09-23）

> **触发**：用户复测反馈——本地 `scripts/start.bat` 启动的应用上，「删除目录 → 再建同名目录被阻拦」「删除回收站的同名条目后新建目录无法操作」，附截图（toast「创建目录失败：同级已存在同名文件或文件夹」）与四步复现流程。
> **基线**：HEAD = `276f9e9`（dev）+ 本批次改动；应用形态 = 生产构建（`dist/`，`start.bat` 同源）。
> **方法**：① 对**用户真实库**做只读取证（复制 `learningtext.db` + WAL 到临时目录，绝不改用户数据）；② 以该副本为夹具真机复现；③ 修复后以**新副本**做端到端验收（启动迁移 + 用户操作序列）。

## 一、真因（此前会话「不可复现」的原因：环境差异）

**取证**（用户库 `D:\appdata\learningtext\LearningText\learningtext.db` 副本，`PRAGMA`/`sqlite_master` 只读查询）：

```sql
-- 用户库 node 表（旧形态）
CREATE TABLE node ( ... virtual_path TEXT NOT NULL UNIQUE, ... )
-- 索引：idx_node_parent_all / idx_node_deleted(partial) / idx_node_parent(partial)
--       / idx_node_parent_name(partial,unique) / sqlite_autoindex_node_1(unique, partial=0 ← 表级约束)
-- 缺 idx_node_virtual_path（部分唯一索引）    user_version = 2
```

**成因**：v1 迁移初次落地时 `virtual_path` 为**列级 `UNIQUE`**（全量约束，回收站行同样占路径）；2026-09-17 软删除域批次（提交 `e17da0f`）把 v1 定义**就地**改为「列不带 UNIQUE + 部分唯一索引 `idx_node_virtual_path (WHERE deleted_at IS NULL)`」——**就地修改对已建库无效**（`user_version` 已为 1/2，迁移不再重放）。用户库创建于该日之前，此后一直停留在旧形态：

- 软删行不让出路径/名称 → **回收站让名语义（FR-VFS-06）整条失效**；
- 服务层重名预查（只查 `deleted_at IS NULL` 活行）放行后，由列级 UNIQUE 兜底报错 → `SQLITE_CONSTRAINT_UNIQUE` → `E_VFS_DUPLICATE_NAME`「同级已存在同名文件或文件夹」= 用户截图 toast 逐字一致；
- 同一根因波及：trash 后**导入同名文件**、**重命名/移动**到被回收站占用的路径、**还原**撞名等全部路径写操作。

**复现（用户库副本 + 用户操作序列，Playwright 驱动生产形态）**：

| 步骤 | 结果 |
| --- | --- |
| ① 新建目录 `复现目录` | ok（树行出现、库中 id=12） |
| ② 删除（行 ⋯ → 删除） | ok（入回收站，树行消失） |
| ③ 再建同名目录 | **toast「创建目录失败：同级已存在同名文件或文件夹」**（缺陷复现，与用户截图一致） |
| ④ 回收站彻底删除该条目 | ok |
| ⑤ 再建同名目录 | ok（id=13）——此后逐步对账：树行 id 与库内事实一致（**无幽灵行**），点击选中、展开、重命名、建子级全部可用 |

**「无法操作」一节的核验**：在用户库副本上按四步复现后逐步对账（树中每个可见行的 `data-node-id` 逐个 `getNode` 验活 + 点击后 `aria-current`/工具栏操作键/行内菜单逐项驱动），**未复现「目录完全无法操作」**——第 ⑤ 步建成的目录可选中、可展开、可建子级、可重命名。判定为**呈现层误判**而非独立缺陷：旧形态下每一次同名写操作都以「失败 toast」收场（用户侧观感为「这个目录没反应/用不了」），叠加行操作入口「⋯」当时**常态透明、仅悬停显形**（用户看不到操作键）。两项分别由本批次的 v3 迁移与 §三 的入口可见化处置；若用户在新构建上仍能复现，请附操作序列与截图按同一探针形态定位。

## 二、修复：v3 迁移（`0003-vfs-path-partial-unique.ts`）

SQLite 无法 `DROP` 列级约束，按官方范式重建表（单迁移单事务，失败整体回滚 + 启动 fail-fast）：

1. **判定旧库**：`pragma_index_list('node')` 存在 `origin='u'`（表级约束自动索引）→ 需修复；健康库直接返回（不触数据）。现行 schema 的唯一性全部由显式 `CREATE [UNIQUE] INDEX`（`origin='c'`）承载，故该判定与「库是旧形态」等价。
2. **读高水位**：`sqlite_sequence` 的 `node` 行（缺失按 0 兜底）。
3. **重建**：`ALTER TABLE node RENAME TO node_v1_legacy` → 建新表（现行 0001 定义）→ `INSERT ... SELECT` **按 `id` 升序**（父节点 id 恒小于子节点，FK 即时校验下父先行）→ `DROP TABLE node_v1_legacy`。
4. **重建索引**：`idx_node_parent_name` / `idx_node_parent` / `idx_node_deleted` / `idx_node_virtual_path`（部分唯一）/ `idx_node_parent_all`。
5. **回填 AUTOINCREMENT 高水位**（只升不降）：purge 过最高 id 的库 `max(id)` 低于历史高水位，不回填会复用 id，破坏 FTS rowid 身份语义。

**验收（用户库新副本，应用启动即迁移）**：

```text
user_version = 3
node 表：无 UNIQUE 约束；索引 = idx_node_parent_all / idx_node_virtual_path(unique,partial)
        / idx_node_deleted(partial) / idx_node_parent(partial) / idx_node_parent_name(unique,partial)
活节点：id=1 根 / id=9 code (2).html / id=15 验收目录R   ← 原数据零丢失
回收站：空；FTS 行数与活非根节点一致；integrity_check ok；foreign_key_check 空
```

操作序列（真实 UI 路径）：建档 → 删除 → **回收站占位下同名重建（成功，无失败 toast）** → 点击选中 → 展开 → 建子级 → 重命名 → 删除 → 回收站彻底删除（应用内确认弹窗）→ **再同名重建（成功）** 全通。

## 三、同批处置的两项呈现层反馈

1. **弹窗样式（用户「弹窗需要优化样式设计」）**：4 处原生 `window.confirm`（彻底删除 / 清空回收站 / 大文件打开 / 未保存退出）统一换 `ConfirmDialog`（应用内浮层，AlertDialog 原语 + 设计系统标尺，文案逐字沿用、破坏色分级、取消项默认聚焦）。M5 打磨对照表 #13 挂账项由此结清；M4 spec 的「confirm 为 Playwright 可驱动选型」被反向满足（应用内浮层由 DOM 直接驱动，E2E 现可验收取消/确认双分支）。
2. **行操作入口可见化（用户「操作键都没有」）**：树行「⋯」由「常态 `opacity-0` 仅悬停显形」改为**常态可见**（前景 muted 档、对比度达标），推翻 M5 降噪裁决并留证（设计系统 §十三）。

## 五、教训固化

1. **迁移脚本一经发布即不可原地修改**（宪法 A.4-3「只升不降」的实质）：本次缺陷的根因就是 2026-09-17 的就地修改——代码侧语义早已正确，但用户库 schema 永远停留旧形态。表结构变更一律**追加新迁移**，并考虑「历史库夹具」型测试（本批已落）。
2. **探针必须在用户真实数据形态上跑**：全新库探针会让「schema 漂移类」缺陷整体隐形（本批教训——前一会话据全新库得出「不可复现」）。凡用户反馈涉及持久化语义，先取真实库副本（只读）对账 schema 与数据。
3. **不可复现≠不存在**：本轮以「副本 + 逐步树/库对账」把「无法操作」从「服务层缺陷」降级为「呈现层误判」，并分别用迁移与入口可见化处置；仍留待用户在新构建上复测确认。
