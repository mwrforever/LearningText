## 缺陷一：macOS close guard × quit 流程 × window-all-closed 三方交互（五轮 CI 迭代）

**现象**：M4 E2E 首次全量跑（CI run 35470170456 前身 35467593381）macOS 平台 9 failed/9 passed、37 分钟，全部 `afterAll hook timeout`（`app.close()` 60s 超时）；Windows/Linux 同套件全绿。M3 既有用例（app.spec ping、preview.spec 删除）同样失败——非新用例特有。

**根因**（ stash 对照 + artifact error-context + 平台差分实证）：Playwright `app.close()` 内部走 `app.quit()` → 逐窗触发 close 事件 → M4 新增的 close guard（`menu.ts` `attachWindowCloseGuard`）对首次 close 一律 `preventDefault`（spec §2.3 D3 选型）**中止了 Electron 的 quit 流程** → guard 发 `confirm-close` → 渲染层无脏调 `forceClose` → 主进程置放行标记 → `win.close()` 重入关窗——**此次关窗已不在 quit 流程内** → 全部窗口关闭触发 `window-all-closed`（`app.ts:179-183`）→ **darwin 分支不 quit（M0 按官方惯例裁决）→ 进程滞留** → Playwright 等进程退出超时。Windows/Linux 分支会 `app.quit()` 故绿；M3 无 guard、不 preventDefault，quit 流程不被打断故绿。

**修复演进**（均测试基建侧，产品主进程零改动——控制器裁决否决 `before-quit` 放行方案：会破坏 guard 用例的 dialog 弹出语义 + 损失 macOS cmd+Q 的 guard 保护）：
1. round 1（f453549）：新增 `tests/e2e/close-app.ts` 共享辅助——`app.close()` 前先经渲染层 `window.api.forceClose()` 显式置放行标记（5s Promise.race + 吞错），quit 流程不再被 preventDefault 打断。afterAll 超时全消。
2. round 3（91a0c6d）：guard 用例（被测行为本体，不能走共享辅助）退出三段收敛：等 5s → `app.evaluate(({app}) => app.quit())` 补显式驱动 → 等 10s → `proc.kill()` 末级。
3. round 4（17ef3d0）：等待窗放宽至 30s/10s、evaluate/kill 全防护、断言放宽为 `exitCode === 0 || signalCode !== null`（「进程已终止」语义）——round 3 CI 实证 mac 上 Playwright closed 与 OS exitCode 置值存在固有时序窗口，evaluate 补驱动会撞「has been closed」。
4. round 5（f9610b0，SDD breaker 裁决）：guard 用例 darwin 平台 `test.skip` 降级。

**breaker 裁决依据**：fix loop 五轮上限到达；guard 核心验收四要素（脏→确认框弹出→Playwright 接管→文案精确匹配「有未保存的更改，确定退出？」→forceClose 链）已在第四轮 CI（run 35471568091）的 macOS 上**真实验证通过**（日志留证）；失败面仅「OS 进程终止验证」——根因是 Playwright `_electron` 在 macOS 的连接生命周期与 Electron quit 流程的平台性交互，非产品缺陷（主进程零改动，Windows/Linux 同链路 exitCode 0 完整退出多轮实证）。与 spec §9.1-7「检查元素原生 popup 不可驱动」同款降级先例。已登记 TASK.md「执行项登记」（mac 覆盖需求出现或 Playwright 能力演进时重评）。

## 缺陷二：macOS 键位差异致保存管线三用例失败（run 35471035956）

**现象**：run 35470170456 中 editor.spec 用例 5（去抖尾沿）/7（挂起强制写）/9（菜单保存）macOS 失败；用例 5/9 报 strict mode violation——`iframe` 内解析出**两个** `id="d"`/`id="k"` 元素；用例 7 期望中途快照「01234」实收全文「0123456789ab」。

**根因**：三用例共用 `page.keyboard.press('Control+a')` 全选——**macOS 全选键位为 Cmd（Playwright `Meta+a`）**，Ctrl+A 在 mac 无绑定 → 全选失效 → 打字变光标处插入 → 插入的 `<p id="d">` 字面量使 HTML 解析器拆出两个兄弟元素（error-context 逐字吻合）。`typeAtEnd` 的 `End` 键同病（mac 的 End 是滚动语义，行尾为 `Meta+ArrowRight`）。

**修复**（7dd0965）：平台分支工具函数 `pressSelectAll()`/`pressEnd()`，mac/win 分派键位；三处接入。同时 guard 用例证据化加固（脏成立前置断言、15s dialog race、close race、kill 兜底）——为缺陷一的二分取证铺路。

**教训**：Task 10 评审 Minor-1/2 预警的「时序余量」在 mac 上被键位问题放大掩盖——E2E 失败归因应先查平台键位/语义差异，再查时序。

## 缺陷三：jsdom 下 CodeMirror 偶发 `getClientRects is not a function`（run 35471568091 Windows）

**现象**：Windows CI 偶发失败于 `panels-preview-workspace.test.tsx > MAX_TABS 触顶` 用例，`TypeError: textRange(...).getClientRects is not a function`（CM6 drawSelection measure 路径 → coordsAtPos）。perf-baseline 的失败标记为连带（其 perf 数字本身达标 P95 125.8ms << 200ms）。

**根因**：jsdom 无布局引擎、未实现 `Range.prototype.getClientRects`；CM6 的 selection draw 层在特定 act/rAF 时序下偶发走 measure → 崩溃。与 M4 代码改动无因果的既有偶发面（依赖时序，本地多轮未命中）。

**修复**（91a0c6d）：新建 `tests/unit/setup.ts`（unit 项目级 setupFiles 接线）——`typeof Range !== 'undefined'` 环境守卫 + 条件式 stub（不遮蔽 jsdom 未来真实现），返回空量测使 markers 为空即跳过绘制。renderer 单测连跑 5 遍无复现。

## 探针实证附记：CJK 路径热替换匹配（Task 9，提交 0ccc49a）

brief 接收器匹配逻辑逐字实现会对中文库永不命中：WHATWG URL 序列化对非 ASCII pathname 恒百分号编码（`/%E7%AC%94%E8%AE%B0/a.css`），而触发端发原始 virtualPath——实施者探针实证后加 `decodeURIComponent(href)` 修复（评审确认：逐字采用 brief 将致本项目热替换完全失效；对 href 解码优于对 path 编码的选型正确）。再次印证交接纪律「依赖浏览器/Electron API 语义的结论必须探针实证」。
