## 五、探针证据（缺陷坐实）

### 5.1 缺陷 1：CSP connect-src（console 权威输出）

```text
[probe][console] error Connecting to 'vfs://x.html/' violates the following Content Security Policy
  directive: "default-src 'self'". Note that 'connect-src' was not explicitly set, so 'default-src'
  is used as a fallback. The action has been blocked.
[probe][console] error Fetch API cannot load vfs://x.html/. Refused to connect because it violates
  the document's Content Security Policy.
[probe] A.fetch结果 {"ok":false,"msg":"TypeError: Failed to fetch"}
```

来源：`src/renderer/index.html` CSP 为 `default-src 'self'; style-src 'self' 'unsafe-inline'; frame-src vfs:`——`frame-src vfs:` 已放行 iframe，但 `connect-src` 缺失。`vfsProtocol.ts` 注释明言「Task 8 E2E 在 app:// 页面以 cors 模式 fetch('vfs://…') 断言 404/200 状态码……均硬依赖此头」，Task 4 已补全响应侧 CORS，但请求侧 CSP 未配套——设计意图落空。

### 5.2 缺陷 2：Blink 与 Node URL 解析不同构（直接对比）

```text
[probe] D.Blink解析 {
 "三斜杠":        { "href": "vfs://probe.html/",  "host": "probe.html", "hostname": "probe.html", "pathname": "/" },
 "两斜杠带host":  { "href": "vfs://h/probe.html", "host": "h",          "hostname": "h",          "pathname": "/probe.html" }
}
[probe] D.Node解析 {"三斜杠":{"href":"vfs:///probe.html","hostname":"","pathname":"/probe.html"}}

[probe][vfs响应] 404 vfs://probe.html/     ← iframe src='vfs:///probe.html'（现行 vfsUrl 产出）变形后到达
[probe][vfs响应] 404 vfs://h/probe.html    ← iframe src='vfs://h/probe.html' 原样到达，handler hostname 校验拒绝
[probe][vfs响应] 404 vfs://probe.html/     ← contentWindow.location.replace('vfs:///probe.html') 同变形
```

**机理**：Blink（GURL）对注册为 standard 的 scheme，把 `scheme:///path`（空 authority）规范化为「首段提为 host、path 置 `/`」；Node WHATWG URL 保留空 host。`vfsParse.ts` 注释「standard scheme 的绝对路径首段恒空串（根标记）」在 Node 侧成立、**在 Blink 发起侧不成立**——spec §2.2-3「WHATWG（Chromium 同构）」前提对空 host 形态不成立。前序任务的 jsdom 单测与 Node 集成测试均无法暴露此差异，E2E 首次实测暴露。
