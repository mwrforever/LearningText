## 一、技术概况（按主题分节，每条带来源 URL）

### 1. better-sqlite3 概貌与版本线

来源：

- 官方 README：https://github.com/WiseLibs/better-sqlite3
- 编译配置（捆绑 SQLite 版本与编译选项，官方 docs/compilation.md）：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/compilation.md
- Release 列表（版本与捆绑 SQLite 对应关系）：https://github.com/WiseLibs/better-sqlite3/releases

要点：

- 定位为 Node.js 下最快、最简单的 SQLite 库，**全同步 API**，宣称"同步 API 反而并发性更好"；支持完整事务、用户自定义函数/聚合/虚拟表、64 位整数、Worker thread。
- **v13.0.0（2026-07-21 发布）是重要分水岭**：首个基于 **N-API（node-addon-api）** 的版本——官方 Release 说明原话："prebuilt binaries should theoretically work across different versions of Node.js and Electron"（预编译二进制理论上跨 Node.js 与 Electron 版本通用），同时**移除了 prebuild-install 依赖**，预编译二进制直接随包发布；平台/架构无预编译时退回安装期源码编译。v13.0.0 另新增 `db.explain()` 与 `preparedStatement.toString()`。
- **捆绑 SQLite 版本随包更新**：v13.0.2 起捆绑 SQLite 3.53.4（v13.0.2 Release："Update SQLite to version 3.53.4"）；master 分支 docs/compilation.md 亦列出捆绑编译选项。
- 捆绑编译选项中与本项目直接相关的（来源：docs/compilation.md "Bundled configuration"）：`SQLITE_ENABLE_FTS5`（FTS5 默认可用）、`SQLITE_DEFAULT_FOREIGN_KEYS=1`（外键约束**默认开启**，与 SQLite 上游默认 OFF 不同）、`SQLITE_DEFAULT_WAL_SYNCHRONOUS=1`（WAL 模式下 synchronous 默认 NORMAL）、`SQLITE_THREADSAFE=2`、`SQLITE_DQS=0`（禁止双引号字符串字面量）、`SQLITE_OMIT_SHARED_CACHE`。
- 升级约束（官方 README "Upgrading"）：升级 better-sqlite3 可能因 semver 大版本带来 API 破坏，也可能因底层 SQLite 版本变化带来数据库行为变化，升级前须查阅 better-sqlite3 Release notes 与 SQLite 官方 changes 页（https://www.sqlite.org/changes.html）。

### 2. 连接生命周期与线程模型

来源：

- API 文档（官方 docs/api.md）：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md
- Worker threads（官方 docs/threads.md）：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/threads.md
- SQLite 事务语义：https://www.sqlite.org/lang_transaction.html

要点：

- `new Database(path, options)` 同步打开（文件不存在则创建）；关键选项：`readonly`、`fileMustExist`（不存在则抛错而非建库）、`timeout`（锁等待毫秒数，**默认 5000**，超时抛 `SQLITE_BUSY`）、`verbose`（每次执行 SQL 的回调）、`nativeBinding`（手动指定 `better_sqlite3.node` 路径）。
- `.close()` 关闭连接，之后不能创建/执行任何语句；官方示例在 `process.on('exit')` 等退出事件中调用。属性 `db.open` / `db.inTransaction` / `db.readonly` / `db.memory` 可用于状态判断。
- 官方对线程的立场（docs/threads.md）："For most applications, `better-sqlite3` is fast enough to use in the main thread without blocking for a noticeable amount of time"；确有很慢的查询时用 worker_threads，**官方示例为每个 Worker 独立 `new Database()` 打开自己的连接**，而非跨线程共享连接。
- SQLite 层面：同一时刻只允许一个写事务；多读可并存（WAL 下读写互不阻塞，见第 4 节）。

### 3. prepared statements 与参数绑定

来源：

- API 文档：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md
- SQLite limits（"Maximum Length Of An SQL Statement" 节，官方明确要求用 host parameters 而非拼接大字面量）：https://www.sqlite.org/limits.html

要点：

- `db.prepare(sql)` 生成 `Statement`；执行族：`.run()`（返回 `info.changes` 与 `info.lastInsertRowid`）、`.get()`（无数据返回 `undefined`）、`.all()`（返回行对象数组）、`.iterate()`（逐行迭代器；官方明确：**如果本来就要取全部行，`.all()` 性能略优**，`.iterate()` 的价值在于逐行消费/提前 break）。语句无需手动 finalize，GC 或关库时自动处理。
- 绑定参数支持匿名 `?` 与命名 `@foo` / `:foo` / `$foo`（可传对象）；类型映射：`NULL↔null`、`REAL↔number`、`INTEGER↔number（或 BigInt，见 docs/integer.md）`、`TEXT↔string`、**`BLOB↔Buffer`**。
- SQLite 官方 limits 页明确：SQL 语句文本长度默认上限 10 亿字节（`SQLITE_MAX_SQL_LENGTH`），且"你不应该那样做（把大值拼进语句），应使用 host parameters"——绑定既免转义防注入，又更快（大值无需反复解析拷贝）。
- `db.exec(sql)` 可执行多语句 SQL（迁移脚本场景），但官方明确它"更慢、不如 prepared statements 安全"，**只应用于执行来自外部源（通常是文件）的 SQL**；出错即停，后续语句不执行，回滚须手动。
- `SqliteError` 带 `code` 属性（SQLite 扩展错误码，如 `SQLITE_CONSTRAINT_UNIQUE`），官方建议错误分支基于官方 rescode 页判断：https://www.sqlite.org/rescode.html

### 4. 事务

来源：

- better-sqlite3 API（`.transaction()` 及 Caveats）：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md
- SQLite 事务文档（官方）：https://www.sqlite.org/lang_transaction.html
- WAL 与 SQLITE_BUSY：https://www.sqlite.org/wal.html

要点：

- `db.transaction(fn)` 返回包装函数：调用时 BEGIN，正常返回 COMMIT，抛异常 ROLLBACK 并继续向上抛；参数/返回值/`this` 均透传。
- 事务变体：默认 `BEGIN`，另有 `.deferred()` / `.immediate()` / `.exclusive()`。SQLite 官方语义：DEFERRED 首次访问库时才真正开事务，首条为 SELECT 则读事务，后续写语句尝试**升级为写事务，失败（他人已持写）则 SQLITE_BUSY**；IMMEDIATE 立即开写事务，他人已持写时立刻 SQLITE_BUSY（fail fast）。
- 嵌套：事务函数内再调事务函数，内层自动降级为 **SAVEPOINT**；内层异常回滚到 savepoint 并重抛，外层未捕获则整体回滚。
- **禁止事项（官方 Caveats 原文要点）**：① 手动 `BEGIN/COMMIT` 与 `.transaction()` 混用不受支持（事务函数内禁止裸 `COMMIT/ROLLBACK`）；② **事务函数不支持 async 函数**——async 函数在首个 `await` 处返回，事务在异步代码执行前就已提交；官方并强调"SQLite 串行化所有事务，让事务跨事件循环 tick 保持打开是非常糟糕的主意"。
- SQLite 可能**未经请求自动回滚事务**（`ON CONFLICT ROLLBACK`、触发器 `RAISE()`、`SQLITE_FULL`/`SQLITE_BUSY` 等错误）；官方给的防御模式：catch 内先检查 `if (!db.inTransaction) throw err;` 再决定继续。能触发自动回滚的错误类别（lang_transaction.md §3）：`SQLITE_FULL`、`SQLITE_IOERR`、`SQLITE_INTERRUPT`、`SQLITE_NOMEM`。
- 显式 `COMMIT` 可能因他连接持有读事务返回 SQLITE_BUSY（事务保持活跃可重试）；WAL 模式下 `EXCLUSIVE` 与 `IMMEDIATE` 等价。

### 5. WAL 模式与 checkpoint

来源：

- SQLite WAL 官方文档：https://www.sqlite.org/wal.html
- better-sqlite3 性能文档（官方 docs/performance.md）：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/performance.md
- PRAGMA 列表（journal_mode / wal_checkpoint / journal_size_limit / busy_timeout 等）：https://www.sqlite.org/pragma.html

要点：

- WAL 优点：写入显著更快、读不阻塞写/写不阻塞读、顺序 IO、更少 fsync。限制：**所有进程必须在同一主机**（网络文件系统不可用，依赖共享内存 wal-index）；进入 WAL 后**不能改 page_size**（须先退出 WAL）；每库多出 `-wal` 与 `-shm` 两个伴生文件。
- **WAL 模式是持久属性**（journal_mode=DELETE 等则不持久）：设过 WAL 的库文件重开后仍是 WAL，且对同一库的所有连接生效。
- 自动 checkpoint：默认 WAL 达 **1000 页**（约 4MB）后由提交事务的线程自动 PASSIVE checkpoint；最后一个连接**干净关闭**时会做最后一次 checkpoint 并删除 `-wal`/`-shm`。可用 `wal_autocheckpoint` 调整/关闭，`wal_checkpoint` 手动触发；手动模式分 **PASSIVE（默认，尽力而为不阻塞他人，可能跑不完）/ FULL / RESTART**（后两者尽力跑完，读者可能被阻塞）；better-sqlite3 官方性能文档给的星饥渴对策示例即 `db.pragma('wal_checkpoint(RESTART)')`。
- **Checkpoint starvation**（官方警告）：并发读永不停歇时 checkpoint 永远跑不完，WAL 无限增长——单进程单连接 + 读事务短暂的用法不会遇到；多连接场景应在 WAL 过大时用 RESTART checkpoint。
- 读性能随 WAL 增大而下降（读需查 WAL）；`synchronous=NORMAL`（better-sqlite3 捆绑默认）下**checkpoint 是唯一的 fsync 点**，事务提交不 sync——换来性能，代价是断电时最近事务可能回滚（官方明示的 durability 权衡，可用 `PRAGMA synchronous=FULL` 覆盖）。
- **WAL 模式下仍可能出现 SQLITE_BUSY** 的边缘情形（官方 wal.html §9）：他连接持有排他锁、最后一连接正在清理 WAL、崩溃后首连正在 recovery——应用应准备应对。
- ⚠️ **WAL-reset bug 通告（官方 wal.html §11，2026-03 披露）**：影响 SQLite 3.7.0–3.51.2，**3.51.3（2026-03-13）修复**，回溯修复至 3.44.6 / 3.50.7；触发条件苛刻（≥2 连接跨线程/进程同时写/checkpoint 的窄窗口竞态），单进程单连接用法不在触发面内。本项目捆绑 SQLite 3.53.4 ≥ 3.51.3，已含修复。

### 6. 迁移：PRAGMA user_version 与迁移执行

来源：

- PRAGMA user_version（官方）：https://www.sqlite.org/pragma.html#pragma_user_version
- 数据库文件格式（offset 60 定义）：https://www.sqlite.org/fileformat.html
- 事务文档（迁移原子性依据）：https://www.sqlite.org/lang_transaction.html
- better-sqlite3 `db.exec` 与 `db.pragma`：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md

要点：

- `PRAGMA schema.user_version` 读写**数据库头偏移 60 处**的 user-version 整数：**32 位大端有符号整数**，新库为 0；SQLite 内部不使用该值，**含义完全由应用定义**（官方 pragma.html 原文："The meaning of the user-version is up to the application"，fileformat.html："The user version is not used by SQLite"）。同类还有 `application_id`（offset 68，用于标识文件类型）。
- user_version 存于数据库头（文件格式固定字段），因此**对它的修改随事务提交/回滚**——这是"迁移 DDL 与版本号原子生效"的底层依据；SQLite 官方不提供迁移框架，顺序迁移、幂等与方向（是否 downgrade）均为应用层约定。
- better-sqlite3 侧执行迁移的正确工具是 `db.exec(迁移 SQL 文件)`（多语句；出错即停、需手动回滚）；读写版本号用 `db.pragma('user_version', { simple: true })`（官方明确 PRAGMA 应使用 `.pragma()` 方法而非普通语句执行，它归一化了 PRAGMA 的怪异行为）。
- 外键开关限制：`PRAGMA foreign_keys` **在事务内是 no-op**（官方 pragma.html 原文），只能在无未决事务时切换——迁移中重建表如需临时关 FK，须在事务外操作。
- 本项目捆绑编译 `SQLITE_DEFAULT_FOREIGN_KEYS=1`（外键默认强制）与 `SQLITE_DQS=0`（双引号一律按标识符解析，写 `"字符串字面量"` 会报错）——迁移脚本与业务 SQL 须在这两个前提下书写。

### 7. FTS5 与 trigram 分词器

来源：

- SQLite FTS5 官方文档（§4.3.4 Trigram / §4.4 外部内容表 / §4.4.4 陷阱 / §6 特殊 INSERT 命令）：https://www.sqlite.org/fts5.html

要点：

- FTS5 虚拟表：`CREATE VIRTUAL TABLE ... USING fts5(...)`；**不允许**声明类型/约束/PRIMARY KEY；无 PRIMARY KEY 声明的 FTS5 表自带隐式 `rowid`（INTEGER PRIMARY KEY 语义），插入时可显式指定 rowid。
- **trigram 分词器**：把文本按**每 3 个连续 Unicode 字符**切为一个 token（不依赖空格与词典），从而把 FTS5 从"词匹配"扩展为**任意子串匹配**——即对中文这类无空格文本提供子串检索能力的官方机制。选项：`case_sensitive`（默认 0 大小写不敏感；**设 1 时只能优化 GLOB，不再优化 LIKE**）、`remove_diacritics`（仅 case_sensitive=0 时可用）。
- trigram 硬性限制（官方 Notes 原文要点）：① **少于 3 个 Unicode 字符的子串在全文本查询中不匹配任何行**；LIKE/GLOB 模式若不含至少一段 ≥3 连续非通配字符，**FTS5 回退为全表线性扫描**；② `detail=none` / `detail=column` 可显著缩小索引（若索引只用于 LIKE/GLOB 值得尝试），但全文查询 token 不能超 3 字符；③ 带 `ESCAPE` 子句的 LIKE 无法利用索引。
- **索引与内容一致性是应用层责任**：外部内容表（`content=`）模式下官方明示"If they are not [consistent], query results may be unpredictable"，并给出触发器同步范式（AFTER INSERT / AFTER DELETE / AFTER UPDATE 三触发器）；普通 FTS5 表 + 应用层在同一事务里同步维护属同一责任模型（官方范式：业务写与索引写同事务）。外部内容表与 contentless 表均**不支持 REPLACE 冲突处理**。
- **删除/更新的顺序陷阱**（官方 §4.4.4.1）：外部内容表 DELETE 时 FTS 需回查内容表取旧值生成反向 token，因此**必须先写 FTS 表、后写业务表**（UPDATE 亦然，UPDATE = DELETE+INSERT）。
- 一致性修复与维护命令（官方 §6）：索引与内容不一致时用 `'rebuild'` 命令**整体丢弃索引并按内容表重建**；`'integrity-check'` 校验一致性；`'optimize'` 把**整个 FTS 索引合并为单个 segment**（官方警告可能耗时很长，可分批的 `'merge'` 命令可用）；`'delete-all'` 清空索引；`'delete'` 命令用于逐行删除索引项（contentless 表删除的唯一途径）。FTS5 表不能 `ALTER`，列集变更只能重建表。

### 8. BLOB 与 SQLite limits

来源：

- SQLite limits 官方文档：https://www.sqlite.org/limits.html
- better-sqlite3 绑定类型映射：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md

要点：

- 字符串/BLOB 最大字节数由 `SQLITE_MAX_LENGTH` 决定，**默认 10 亿（1,000,000,000）字节**；且 INSERT/SELECT 处理期间整行编码为单个 BLOB，故该值同时限制行大小。上限可调但安全敏感应用官方建议**调低**。本项目 50MB 单文件上限远低于默认上限，属应用层约束（应在写入前校验，而非依赖数据库报错）。
- 大值必须走 **host parameters 绑定**（官方 limits 页原文反对把大值拼进 SQL 字面量）；better-sqlite3 中 BLOB 即 Node `Buffer`。
- 大结果集：`.iterate()` 逐行消费避免一次性物化整表；但**单行内的 BLOB 仍会整体物化为 Buffer**（better-sqlite3 不提供增量 BLOB I/O——API 文档无对应能力，SQLite C API 的 `sqlite3_blob_open` 系列未暴露），50MB 级 BLOB 读写会在主进程同步占用等量内存并阻塞事件循环相应时长。
- 其他相关默认上限：宿主参数个数 `SQLITE_MAX_VARIABLE_NUMBER` **3.32.0（2020-05-22）起默认 32766**（此前 999）——批量 IN/VALUES 须控制在参数数内；SQL 语句长度默认 10 亿字节；JOIN 表数上限 64。

### 9. 备份与"checkpoint 后整文件复制"的依据

来源：

- SQLite WAL 官方文档 §4（WAL 文件是持久状态）与 §3.1（关闭时最终 checkpoint）：https://www.sqlite.org/wal.html
- SQLite Online Backup API 官方文档（含 VACUUM INTO 替代方案）：https://www.sqlite.org/backup.html
- better-sqlite3 `db.backup()`：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md

要点：

- **整文件复制必须先处理 WAL**：官方 wal.html §4 原文要点——WAL 文件是数据库持久状态的一部分，复制/移动库时必须与库文件同行；**库文件与 WAL 分离会导致已提交事务丢失甚至库损坏**；唯一安全的"移除 WAL 文件"方式是正常 open 后 clean close。
- 最后一个连接干净关闭时自动做最终 checkpoint 并删除 `-wal`/`-shm`（wal.html §3.1/§6）——因此"应用空闲/退出时 checkpoint，之后复制单个 .db 文件"是官方语义下自洽的冷备路径；checkpoint 方式见 `PRAGMA wal_checkpoint`（PASSIVE/FULL/RESTART，见第 5 节）。
- 官方提供的**在线备份**替代：① Online Backup API（逐页复制，目标成为源库的 bit-wise 快照；期间源库仅在被读的短暂窗口持锁；同一连接边写边备份会自动并入备份，**他连接写入会导致备份重启**）；② `VACUUM INTO`（对活库做压缩副本）；③ `sqlite3_rsync`（跨机）。better-sqlite3 将 Backup API 封装为 `db.backup(destination, { progress })`，返回 Promise，默认每轮事件循环传 100 页、可用 progress 回调调速（返回 0 暂停），备份期间数据库可正常使用；父连接关闭时未完成备份自动中止。另有 `db.serialize()` 返回整库内存 Buffer。
- 本项目既定方案"WAL checkpoint 后整文件复制"与官方语义兼容；规范候选只需固化"复制前必须 checkpoint 且校验完成，禁止复制残留未 checkpoint 的 -wal 存在时的裸 .db"这类边界。

### 10. Electron 原生模块约束（ABI / electron-rebuild / 打包）

来源：

- Electron 官方教程 Using Native Node Modules：https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules
- @electron/rebuild 官方 README：https://github.com/electron/rebuild
- better-sqlite3 官方 troubleshooting（Electron / Windows 节）：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/troubleshooting.md
- better-sqlite3 v13.0.0 Release（N-API 化说明）：https://github.com/WiseLibs/better-sqlite3/releases

要点：

- **ABI 机制**：Electron 自带的 Node 与系统 Node ABI 不同（如 Electron 用 Chromium 的 BoringSSL 而非 OpenSSL），原生模块必须**针对 Electron 重编译**，否则报 `NODE_MODULE_VERSION` 不匹配错误。**每次升级 Electron 通常都需要重建原生模块**（官方 Troubleshooting 原文："After you upgrade Electron, you usually need to rebuild the modules"）。
- **@electron/rebuild**（实测 latest 4.2.0）：`npm install --save-dev @electron/rebuild` 后运行 `electron-rebuild`（Windows 用 `electron-rebuild.cmd`）；**每次 `npm install` 新包后都要重跑**；自动探测 Electron 版本、下载头文件并重建（支持 `prebuild-install` 下载对应 Electron 预编译产物或源码编译）；要求 **Node v22.12.0+**；Electron Forge 打包流程**自动**集成该工具。
- **better-sqlite3 v13.0.0 起（N-API）显著放宽**：预编译二进制理论上跨 Node/Electron 版本通用，理论上可减少对 electron-rebuild 的依赖；v13.0.0 之前（12.x 及更早）为 NODE_MODULE_VERSION 体系，**必须** electron-rebuild。ⓘ "N-API 版 better-sqlite3 在 Electron 打包链路中是否可完全跳过 rebuild"官方文档未逐字给出操作指引，记 {待调研项}，稳妥做法是保留 rebuild 步骤兜底（无预编译平台仍需源码编译）。
- **打包（asar）**：better-sqlite3 官方 troubleshooting 原文——使用 app.asar 时**原生库必须 unpack**；Electron Forge 应启用 auto-unpack-natives 插件。
- **Windows 构建环境**（官方 troubleshooting）：Node 安装时勾选"Tools for Native Modules"（装 Chocolatey/Visual Studio/Python）；**项目路径不得含空格与特殊字符**（node-gyp 转义问题）；安装失败时删 `node_modules` 与 `$HOME/.node-gyp` 后重装。Windows 下原生模块须 `win_delay_load_hook: true`（Electron 4.x+ 符号由 electron.exe 导出，无 node.dll；缺失报 `Module did not self-register`）。
- 其他：安装失败先确认 better-sqlite3 为最新版、Node 为官方支持版本；复杂打包链路移动/拼接 JS 文件导致找不到 `.node` 时，用 `new Database(path, { nativeBinding })` 显式指定。

### 11. 同步阻塞的界限（多大事务会卡主进程事件循环）

来源：

- better-sqlite3 docs/threads.md：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/threads.md
- better-sqlite3 docs/api.md 事务 Caveats：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md
- better-sqlite3 README（何时本库不适用）：https://github.com/WiseLibs/better-sqlite3

要点：

- **官方没有给出"多少毫秒/多大事务会卡事件循环"的量化阈值**——所有同步语句（含事务整体）都会阻塞主进程事件循环至执行完毕，阻塞时长与语句耗时成正比。官方定性指引仅有：① "对大多数应用，主线程使用 better-sqlite3 不会产生可感知阻塞"；② "执行需要 1 秒完成且高并发用户的查询"被官方列为不适合本库的场景示例；③ 慢查询应移入 worker_threads（每 Worker 独立连接）。
- 官方对事务的硬性风格约束：**事务不得跨事件循环 tick 保持打开、事务函数内禁 async**（见第 4 节）。
- 结论：{待调研项}——官方无量化数值可引；规范条目只能以"交互路径单事务时长预算 + 大批量操作移出交互路径/移入 worker"的定性形式成立，具体预算毫秒数须由项目实测自定。

## 四、关键发现摘要（供宪法起草者速览）

1. **better-sqlite3 13.0.0 起 N-API 化**是 A.5 最大变量：预编译二进制理论跨 Node/Electron 通用，但仍保留 electron-rebuild 兜底（无预编译平台 + 官方未给免 rebuild 指引）。
2. **WAL 下数据库与 `-wal` 是一体**：备份/复制前必须 checkpoint（A4-14 的官方依据），干净关闭自带最终 checkpoint——单例连接 + 优雅关闭天然满足。
3. **FTS 索引一致性是应用层责任**：业务写与索引写同事务（A4-6）、删除先索引后业务（A4-17）、trigram 三条查询退化边界（A4-16）是宪法必须固化的三条硬规则。
4. **user_version 存于数据库头、随事务原子提交**，配合 `db.exec` + 事务包裹即可实现无框架的顺序幂等迁移；`foreign_keys` 事务内 no-op 是迁移脚本唯一易踩的 PRAGMA 陷阱。
5. **官方无"多大事务卡事件循环"的数值**，A5-6 只能定性落地；捆绑 SQLite 3.53.4 已包含 2026-03 披露的 WAL-reset bug 修复（≥3.51.3）。
