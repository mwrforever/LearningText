## 一、技术概况（逐主题要点，均带来源 URL）

### 1. GitHub Actions 工作流语法与最佳实践

来源：
- 工作流语法参考（官方）：https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax
- 使用限制（官方）：https://docs.github.com/en/actions/reference/limits
- 作业变体（matrix include/exclude，官方）：https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/run-job-variations

要点：

- **触发（on push/pull_request）**：`push` 与 `pull_request` 均支持 `branches`/`tags`/`paths` 过滤；同一事件不能混用 `branches` 与 `branches-ignore`；同时定义分支与路径过滤时两者需同时满足。
- **门禁关键陷阱**：官方明确——工作流因路径/分支过滤或 commit message 被**跳过**时，其关联检查会停留在 **Pending** 状态，设置了必需检查（required check）的 PR 会被**阻塞无法合并**。因此 CI 门禁工作流**不应使用 paths/paths-ignore 过滤**。
- **concurrency（取消旧跑）**：同一 concurrency 组同时只允许一个运行；推荐组名包含 `github.workflow` 前缀（组名要求跨工作流唯一）+ `github.ref`（PR 场景可用 `github.head_ref || github.run_id` 兜底）；`cancel-in-progress: true` 表示新运行入队时取消旧的进行中运行。
- **permissions（最小权限）**：顶层 `permissions` 作用于全部 job，job 级可覆盖；**一旦显式指定任何权限，未指定的全部自动设为 none**；快捷值 `read-all`/`write-all`/`{}`（全禁）。需要创建 Release 的 job 才提升 `contents: write`。官方警示 `pull_request_target` 即使来自 fork 也授予读写 token，应避免使用。
- **timeout-minutes（作业超时）**：该字段定义于工作流语法参考的 `jobs.<job_id>.timeout-minutes` 节；使用限制页明确 **GitHub 托管 runner 上单个作业最长 6 小时**，超时即失败终止（不可提升）；自托管最长 5 天；单次工作流运行最长 35 天。
- **matrix 与 fail-fast**：`strategy.matrix` 支持 `include`（追加/扩展组合）与 `exclude`（剔除组合）；`fail-fast`（工作流语法参考给出默认值 `true`：任一非容错矩阵作业失败即取消其余进行中与排队中的作业，收集全部平台结果时应显式设为 `false`）；`max-parallel` 限制同时运行的矩阵作业数。单次运行矩阵作业数上限 256。
- **并发额度**：Free 计划下总并发作业 20，其中 **macOS 并发上限 5**；**公共仓库使用标准托管 runner 完全免费**（仅 Larger runner 收费）——三平台矩阵对单人公共仓库项目零成本可行。来源：https://docs.github.com/en/actions/reference/limits 与 https://docs.github.com/en/billing/concepts/product-billing/github-actions

### 2. 分支保护规则 Required status checks（门禁阻断的落地方式）

来源：
- 关于受保护分支（官方）：https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches
- 管理分支保护规则（官方）：https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule

要点：

- 路径：仓库 Settings → Branches → "Add classic branch protection rule"，按分支名模式（如 `main`）创建规则；分支可以尚不存在。
- 门禁核心开关：**"Require status checks to pass before merging"**——勾选后，所有被列为必需的检查必须达到 **successful、skipped 或 neutral** 状态才允许合并。
- **strict 模式**：即 "Require branches to be up to date before merging"，要求分支先更新到与主干一致再触发检查（必需状态检查的默认行为）；代价是主干更新后需要重跑构建，换来"合并即通过"的确定性。
- **命名唯一性**：使用必需检查时，各工作流中的 **job 名称必须跨全部工作流唯一**，否则产生"模糊的检查结果（ambiguous status check）"，会直接阻塞 PR 合并。
- 绕过通道管控："Restrict who can push" 适用于 GitHub Free 组织的公共仓库与 Team/Enterprise Cloud 仓库；绕过列表（bypass list）仅组织仓库可配。**公共仓库的 classic 分支保护本身可用**。更灵活的替代机制是 rulesets（同一时间一条规则生效的场景下官方建议考虑）。
- 结论：**"任何检查失败阻断合入主干"的落地方式 = classic 分支保护 + 必需状态检查 + strict 更新要求**；工作流层面的任何配置都只是"上报检查"，真正阻断靠分支保护规则。

### 3. 缓存（npm / Electron 二进制 / Playwright 浏览器）

来源：
- actions/setup-node 官方 README：https://github.com/actions/setup-node
- actions/cache 官方 README：https://github.com/actions/cache
- @electron/get 官方 README（Electron 二进制缓存路径）：https://github.com/electron/get
- electron-builder 官方 GitHub Actions 指南（含缓存路径建议）：https://github.com/electron-userland/electron-builder/blob/master/website/docs/features/github-actions.md
- Playwright 官方 CI 指南：https://playwright.dev/docs/ci

要点：

- **actions/setup-node**（当前大版本 v7）：内置 `cache: npm` 复用 actions/cache，以 lockfile（`package-lock.json` 等）哈希作为缓存键的一部分；**明确不缓存 `node_modules`**；支持 `node-version-file`（`.nvmrc`/`package.json` 等）。
- **actions/cache**（当前大版本 v6）：缓存按 **key + version + 分支** 三元组隔离；version 由压缩工具（随 runner OS 不同）与缓存路径共同哈希生成，因此 **Windows 产生的缓存无法在 Linux 恢复**（即跨 OS 天然隔离）；每仓库缓存上限 **10 GB**，超限按最近访问时间淘汰，**7 天未访问的缓存会被清除**；`cache-hit` 输出仅在主 key 精确命中时为 `'true'`，经 `restore-keys` 前缀回退命中的为 `'false'`（此时不能跳过安装）。
- **Electron 二进制缓存路径**（@electron/get）：Linux `~/.cache/electron/`、macOS `~/Library/Caches/electron/`、Windows `%LOCALAPPDATA%/electron/Cache`；镜像可用 `ELECTRON_MIRROR` 覆盖。electron-builder 官方 Actions 指南还建议一并缓存 `~/.cache/electron-builder`（Windows 为 `~\AppData\Local\electron`），key 基于 lockfile 哈希。
- **Playwright 浏览器二进制**：官方态度明确——**"不推荐缓存浏览器二进制"**，因为恢复缓存耗时与重新下载相当，且 Linux 系统依赖不可缓存；若坚持缓存需以 Playwright 版本哈希作 key。本项目采用官方推荐：不缓存浏览器，每次 `playwright install --with-deps`。

### 4. better-sqlite3 在 Electron 下的原生重编译

来源：
- better-sqlite3 troubleshooting（官方）：https://github.com/WiseLibs/better-sqlite3/blob/master/docs/troubleshooting.md
- better-sqlite3 主 README：https://github.com/WiseLibs/better-sqlite3
- @electron/rebuild 官方 README：https://github.com/electron/rebuild
- electron-builder `npmRebuild` 选项定义（源码注释，含默认值）：https://github.com/electron-userland/electron-builder/blob/master/packages/app-builder-lib/src/configuration.ts
- electron-builder GitHub Actions 指南（"原生模块问题应使用 npm ci，electron-builder 会自动为 Electron 版本重建"）：https://github.com/electron-userland/electron-builder/blob/master/website/docs/features/github-actions.md

要点：

- better-sqlite3 官方 troubleshooting 原话：**"If you're using Electron, use electron-rebuild"**；并要求使用 asar 打包时**所有原生库必须 unpack**（`.node` 二进制无法从 asar 归档内直接加载）。
- better-sqlite3 的预编译二进制按"主要平台/架构"分发且面向 Node 运行时（README 未承诺 Electron 运行时）；即 **Vitest 等 Node 侧测试可直接用预编译二进制，Electron 进程内必须用针对 Electron ABI 编译的版本**。
- **@electron/rebuild**（当前 4.2.0）：针对项目所用 Electron 版本对应的 Node 头文件重编译原生模块（头文件默认从 `https://www.electronjs.org/headers` 下载，可经 `ELECTRON_REBUILD_DIST_URL` 覆盖）；`-f`（force）强制重编、`-w` 指定模块；要求 Node ≥ 22.12；提供可编程 API 可嵌入任意构建流程。
- **electron-builder 的 `npmRebuild` 默认为 `true`**：打包前自动在 `node_modules` 上运行 `@electron/rebuild`，保证原生模块匹配 Electron ABI（另有 `rebuildMode: sequential | parallel`，默认 sequential，官方注释提示 parallel 在内存受限的 CI 上可能耗尽资源；`nodeGypRebuild` 默认 `false`，官方注释称多数项目应保持 false、依赖 @electron/rebuild）。
- **CI 工程含义（本项目的关键决策点）**：Playwright E2E 经 `_electron.launch` 启动的是**开发形态的应用**（非 electron-builder 产物），因此 **E2E 前必须显式执行 @electron/rebuild**，让 better-sqlite3 变为 Electron ABI 版本；而 electron-builder 打包阶段的 ABI 匹配由 `npmRebuild` 默认机制兜底，无需重复手跑。
- 版本注意：当前 Electron 稳定版 44.x 已**移除 32 位目标**（`ia32`/`armv7l` 仅支持 Electron ≤ 43），electron-builder 文档明示配置 32 位目标会直接报错。来源：https://github.com/electron-userland/electron-builder/blob/master/website/docs/features/multi-platform-build.md

### 5. Playwright 官方 CI 指南（含 Electron 场景）

来源：
- Playwright CI 指南：https://playwright.dev/docs/ci
- Playwright Electron API（`_electron`）：https://playwright.dev/docs/api/class-electron

要点：

- 官方 GitHub Actions 流程：`npm ci` → `npx playwright install --with-deps`（Linux 同时装浏览器与系统依赖）→ `npx playwright test`；测试报告用 `upload-artifact` 上传（失败也传，条件用 `if: !cancelled()` 语义）。
- **CI 稳定性**：官方推荐 **CI 环境把 workers 设为 1**（"prioritize stability and reproducibility"）；重试（retries）为官方列出的 CI 稳定性手段。
- **分片（sharding）**：以矩阵作业分发测试；官方同时警告 `--only-changed` 类增量跑法是启发式、可能漏测，**必须始终保留全量测试套兜底**——与本项目"严格门禁"原则一致，不建议增量门禁。
- **Linux 有头运行**：需要 Xvfb（官方 Docker 镜像与 GitHub Actions 环境已预装，命令前缀 `xvfb-run`）；Electron 主进程应用通常需有头/Xvfb 环境启动。
- **浏览器缓存**：不推荐（见第 3 节）。
- **Electron 自动化**：`_electron.launch({ executablePath, args })`，`executablePath` 缺省用 playwright 包内 Electron；`args` 传主脚本；`firstWindow()` 等待首窗口；`evaluate()` 在**主进程**执行；原生对话框不会被自动拦截、需主进程 stub；启动超时默认 30 秒；要求 Electron 14+（当前 44.x 满足）；该能力官方标注为**实验性**（版本升级可能带破坏）。

### 6. electron-builder 官方 CI/发布指南

来源：
- 多平台构建：https://github.com/electron-userland/electron-builder/blob/master/website/docs/features/multi-platform-build.md
- GitHub Actions 指南：https://github.com/electron-userland/electron-builder/blob/master/website/docs/features/github-actions.md
- 发布（publish）：https://github.com/electron-userland/electron-builder/blob/master/website/docs/publish.md
- 代码签名总览：https://github.com/electron-userland/electron-builder/blob/master/website/docs/features/code-signing/code-signing.md

要点：

- **多平台**：官方开篇警告"不要指望在一个平台上构建所有平台"——**macOS 目标（尤其签名）只能在 macOS 上构建**；Linux 可经 Wine 交叉构建 Windows NSIS（NSIS 不需要 Mono）；**应用含原生依赖时不能在 Docker 中构建 Windows 目标**（本项目含 better-sqlite3，正好命中）。⇒ 结论：CI 必须三平台原生矩阵。
- **GitHub Actions 指南推荐**：`os: [macos-latest, windows-latest, ubuntu-latest]` 矩阵 + `runs-on: ${{ matrix.os }}`；生产级工作流按平台拆独立 job；发 Release 的 workflow **必须声明 `permissions: contents: write`** 否则报错；日常构建 `--publish never`。
- **发布**：GH_TOKEN/GITHUB_TOKEN 存在时默认 provider 为 GitHub；**v27 起移除隐式发布，必须显式 `--publish`**（`onTag` / `onTagOrDraft` / `always` / `never`）；CI 检测到 tag push 时自动规则为 `onTag`：**创建 draft release（如不存在）并上传产物**；官方推荐"draft 挂最新产物 → 人工验证后手动 publish"的流程。注意：npm 最新稳定为 26.15.3，而仓库 master 文档已包含 v27 破坏性变更（如 `electronDownload` 更名 `electronGet`、隐式发布移除），落地时以所安装版本的文档为准。
- **签名（secrets 占位的依据）**：环境变量清单——macOS：`CSC_LINK`（base64 .p12）+ `CSC_KEY_PASSWORD`，公证另需 `APPLE_ID`、`APPLE_APP_SPECIFIC_PASSWORD`、`APPLE_TEAM_ID`；Windows：`WIN_CSC_LINK` + `WIN_CSC_KEY_PASSWORD`（未设时回退 `CSC_LINK`/`CSC_KEY_PASSWORD`），云端签名走 `AZURE_*` 三件套。**未提供凭据时默认静默跳过签名**（官方提醒可能导致"静默未签名的生产构建"）；`forceCodeSigning: true` 可把"缺凭据"从静默跳过变成**构建失败**——证书就绪后应开启，形成"无证书不得发布"的硬门禁（当前无证书阶段开启会导致构建必失败，需在方案中处理该时序）。secrets 一律不入库；Windows 环境变量上限 8192 字符，base64 证书超限时重新导出不含完整证书链。

### 7. husky + lint-staged 在 CI 与本地的分工

来源：
- husky 官方文档：https://typicode.github.io/husky/
- Git 官方 githooks 文档（hooks 位置与传播性）：https://git-scm.com/docs/githooks
- Git 官方 git-commit 文档（`--no-verify` 绕过钩子）：https://git-scm.com/docs/git-commit
- lint-staged 官方 README：https://github.com/lint-staged/lint-staged

要点：

- husky 基于 Git 原生 `core.hooksPath` 管理全部 13 个客户端钩子，经 npm `prepare` 脚本安装；本质是**本地开发机**机制。
- Git hooks 位于 `$GIT_DIR/hooks`，**`git clone` 不会复制钩子**——因此 CI 环境天然不执行 husky 钩子；且 `git commit --no-verify` 可显式绕过本地钩子。
- lint-staged 只对**暂存区文件**执行 lint/格式化，执行前自动 stash 备份、出错回滚；官方配合方式是在 `.husky/pre-commit` 中执行 `npx lint-staged`；并支持 `--diff="main...branch"`（CI 增量）与 `--all`（全量）模式。
- **分工结论**：husky + lint-staged = 本地**快速反馈层**（秒级、只查改动文件、可被绕过，不构成门禁）；CI = **权威门禁层**（全量 lint / 格式检查 / 类型检查，不可绕过）。两层检查规则必须一致（同一份 ESLint/Prettier 配置），否则会出现"本地过了 CI 不过"。CI 中不使用 lint-staged 做门禁（其对象是暂存区这一本地概念）。

{待调研项}：
- `actions/checkout`、`actions/upload-artifact` 等辅助 action 的当前最新大版本未逐一核对（本文焦点在门禁设计），M0 落地时以各官方仓库最新 tag 为准。原因：与门禁语义无关，且版本迭代快。
- Playwright `retries` 在 CI 页仅在导航中列出、未展开推荐值；落地时可参考 https://playwright.dev/docs/test-retries 并以实测稳定性定值。
- `ubuntu-latest`/`windows-latest`/`macos-latest` 指向的具体镜像版本随时间变化（如 Ubuntu 22.04→24.04），涉及"Ubuntu 22.04+"矩阵承诺时，落地时核对 https://github.com/actions/runner-images 的 latest 映射。

## 三、三套 CI 门禁方案（核心交付物）

三套方案在**严格程度 / 反馈速度 / 配置复杂度**三个维度上刻意拉开差距：

| 维度 | 方案 A：三平台全量严格矩阵 | 方案 B：分层快速反馈 | 方案 C：严格+发布就绪 |
| --- | --- | --- | --- |
| 严格程度 | 最高（PR 即全平台+E2E） | 中（PR 仅 Node 侧，主干全量） | 最高（= A，另加发布链门禁） |
| PR 反馈速度 | 慢（估 15–30 分钟） | 最快（估 3–8 分钟） | 慢（同 A） |
| 配置复杂度 | 中（1 个工作流） | 中（2 个工作流） | 高（2 个工作流 + secrets 体系） |

### 方案 A：三平台全量严格矩阵（推荐基线）

**工作流结构**：单一工作流（对应未来的 `.github/workflows/ci.yml`），三平台矩阵并行，每个矩阵作业执行完整链路。

**触发与分支保护**
- 触发：`pull_request`（目标 main）+ `push` 到 main + `push` `v*` tag。不用 paths 过滤（防 Pending 自锁）。
- concurrency：组名 = 工作流名 + ref，`cancel-in-progress` 开启（旧跑立即取消）。
- permissions：顶层最小化（只读），无发布 job。
- 分支保护（main）：必需检查 = 三个平台作业的检查名（命名带平台前缀，保证唯一）+ 勾选"分支须与主干同步"（strict）。任何一项未通过 → GitHub 层面禁止合并，无绕过通道（仓库管理员也默认受限，可依团队约定决定是否豁免管理员）。

**矩阵设计**
- `os: [ubuntu-latest, windows-latest, macos-latest]`，`fail-fast: false`（一平台失败不取消其余平台，一次性收集全部结果）；不设 `max-parallel`（默认全并行；Free 计划 macOS 并发 5，单人无压力）。
- 每个作业显式 `timeout-minutes`（按"安装+质量+测试+rebuild+E2E+打包冒烟"总预算给定，超时即门禁失败）。

**流水线阶段与门禁语义**（每个矩阵作业内顺序执行，任一步非零退出 = 该检查失败 = 阻断合入）
1. **安装**：setup-node（版本来自 `node-version-file`）→ `npm ci`（锁文件不一致即失败，天然校验 lockfile）。门禁语义：依赖可复现安装。
2. **静态质量**：Prettier 格式检查 + ESLint + `tsc --noEmit`。门禁语义：代码风格与类型严格模式全平台一致（三个平台重复执行质量检查，顺带捕获平台差异引入的解析差异）。
3. **单元 + 集成测试（Vitest，Node 侧）**：better-sqlite3 使用 Node 预编译二进制。门禁语义：业务逻辑与存储层逻辑正确。
4. **原生模块重编译**：`@electron/rebuild -f -w better-sqlite3`（针对当前 Electron ABI）。门禁语义：**本项目最高风险点**——原生模块能否匹配 Electron ABI，三平台全部验证。
5. **E2E（Playwright `_electron`）**：启动真实 Electron 应用（已含步骤 4 的重编译产物），Linux 侧前置 `playwright install --with-deps` 与 Xvfb；workers=1、启用 retries；失败仍上传 HTML 报告（上传步骤不拦截门禁，仅测试本身拦截）。门禁语义：主进程/渲染进程/IPC/SQLite 全链路可用。
6. **打包冒烟（electron-builder，`--publish never`）**：分别产出 NSIS / DMG / AppImage 验证可打包（内部由 `npmRebuild` 兜底 ABI），产物上传为短期保留的 artifact 供人工抽查。门禁语义：三平台安装包可产出（macOS 签名缺失为已知占位，见方案 C）。

**缓存策略**：setup-node `cache: npm`（lockfile 哈希 key）；actions/cache 缓存 Electron 下载 zip（路径按 OS 映射 `~/.cache/electron` 等，key 含 runner OS + Electron 版本）；一并缓存 `~/.cache/electron-builder`；Playwright 浏览器不缓存（官方建议）；Playwright/系统依赖每次安装。

**产物处理**：仅上传 artifact（安装包 + E2E 报告），不发布。artifact 设置较短保留期。

**优点**：需求字面满足——"任何检查失败阻断合入主干"且失败不可能来自未验证的平台；better-sqlite3 ABI 与 E2E 风险在 PR 阶段即暴露；单文件配置，心智负担最小；公共仓库免费。
**缺点**：PR 反馈最慢；三平台重复质量检查有少量冗余耗时；矩阵作业中一步失败需整作业重跑（可用作业内缓存缓解）。
**适用场景**：单人 + AI 代理开发、公共仓库、对主干质量零容忍的项目——即本项目当前状态。

### 方案 B：分层快速反馈（PR 轻量门禁 + 主干全量矩阵）

**工作流结构**：两个工作流——`PR 门禁`（轻量）与 `主干全量`（矩阵）。

**触发与分支保护**
- PR 门禁：`pull_request` 目标 main → 仅 ubuntu-latest 单作业：安装 → 静态质量 → Vitest 单元+集成（全部 Node 侧，不 rebuild、不 E2E、不打包）。
- 主干全量：`push` 到 main + `v*` tag → 与方案 A 相同的三平台矩阵全链路（含 rebuild/E2E/打包冒烟）。
- 分支保护（main）：必需检查 = PR 门禁作业 + 主干全量的三个平台作业（共 4 个）+ strict。主干 push 的失败同样构成"必需检查失败"，配合保护规则可阻止后续合并直至修复（主干红灯修复期间主干不可再进新代码）。

**流水线阶段**：同方案 A 的阶段 1–3 构成 PR 层；阶段 1–6 构成主干层。各层门禁语义不变，但 **PR 层门禁语义缺口明确**：Electron ABI、跨平台行为、E2E 全链路问题**在合入主干后才暴露**。

**缓存策略**：与方案 A 相同（两层共享同组缓存，分支缓存隔离规则下主干缓存可被 PR 分支读取，命中率更好）。

**产物处理**：主干层上传 artifact；PR 层无产物。

**优点**：PR 反馈最快（估 3–8 分钟），迭代流畅，AI 代理高频提交场景体验好；额度消耗最低。
**缺点**：**与"严格门禁"需求存在原则性偏差**——缺陷先入主干再暴露，主干红灯是常态而非例外；better-sqlite3 ABI 回归可能污染主干历史；两文件配置，检查名管理与语义解释成本更高。
**适用场景**：迭代速度优先、可接受"主干红灯快速修复"文化、E2E/跨平台问题低频的项目。

### 方案 C：严格 + 发布就绪（A 基础上加 electron-builder 发布与签名占位）

**工作流结构**：两个工作流——`CI`（与方案 A 完全一致）+ `Release`（tag 触发的三平台发布矩阵）。

**触发与分支保护**
- CI 工作流与分支保护：与方案 A 完全相同（PR + main push 门禁不变，**发布链不替代也不削弱 PR 门禁**）。
- Release 工作流：`push` `v*` tag 触发 + `workflow_dispatch` 手动补发；发版前置条件（tag 上的 CI 全绿）可由发布作业复验或以分支保护+strict 保证（tag 指向的提交必然已通过主干门禁）。
- Release 作业 permissions：仅发布作业提升 `contents: write`（创建 draft release 并上传资产），其余作业保持只读。

**矩阵设计**：`os: [macos-latest, windows-latest, ubuntu-latest]`，`fail-fast: false`；可选一个汇总作业依赖全部平台作业成功后再执行（作为"发布就绪"的单一检查点）。

**流水线阶段与门禁语义**
1. **构建**：同方案 A 阶段 1–5（安装/质量/测试/rebuild/E2E），保证**进入发布流程的代码与门禁通过的代码是同一份验证结果**。
2. **打包与发布**：electron-builder 以 `--publish onTagOrDraft`（或等价的 tag 规则）产出 NSIS / DMG / AppImage 并上传到 **draft release**。门禁语义：任何平台打包失败 → 该 tag 不存在完整 draft。
3. **人工复核门禁**：draft release 挂齐三平台产物后，由人核对并在 GitHub Releases 手动 publish（官方推荐流程；publish 动作本身即发布闸门）。

**签名占位（当前无证书阶段的落地语义）**
- 预置仓库 secrets 占位（暂存空值/占位注释，中文注明用途）：`MAC_CSC_LINK`、`MAC_CSC_KEY_PASSWORD`、`APPLE_ID`、`APPLE_APP_SPECIFIC_PASSWORD`、`APPLE_TEAM_ID`、`WIN_CSC_LINK`、`WIN_CSC_KEY_PASSWORD`。
- 签名步骤设计为"secrets 存在才注入"的条件行为：当前阶段产出显式标记为未签名的产物；证书就绪后仅需填入 secrets，无需改工作流。
- **`forceCodeSigning` 开启时序**：当前无证书期**不能**开启（否则按官方语义构建必失败，发布链全断）；证书入 secrets 后开启，届时"缺证书"从静默跳过升级为构建失败，形成"无签名不得发布"的硬门禁。macOS 公证（notarization）同样以 `APPLE_*` secrets 就绪为前置。

**缓存策略**：与方案 A 相同。

**产物处理**：三平台安装包 → draft release 资产（非 artifact）；`latest.yml` 等自动更新元数据随 draft 生成；E2E 报告照常 artifact。

**优点**：A 的全部优点 + 发布链自动化与 draft 人工闸门；签名/公证 secrets 就绪后零改造接入；"构建即发布候选"消除手工打包差异。
**缺点**：复杂度最高（secrets 体系、发布参数、平台差异排错）；E2E+发布串行在 tag 事件上耗时最长；当前无证书阶段签名语义需要团队自觉区分"未签名产物"的用途边界。
**适用场景**：临近对外分发里程碑（需真实安装包交付）时启用；CI 部分与方案 A 相同，可平滑演进。

## 四、调研推荐及理由

**推荐：M0 基线采用方案 A；方案 C 作为发布里程碑（需要对外分发安装包时）在 A 之上的平滑演进（A 的 ci.yml 原样保留，仅新增 release 工作流）；方案 B 仅在 A 实测反馈时间确实不可接受时作为降级备选。**

理由：
1. **需求匹配**：需求关键词为"严格门禁——任何检查失败阻断合入主干，禁止人工绕过"。方案 B 的分层设计意味着 Electron ABI、跨平台、E2E 问题在合入主干后才失败，属于"事后拦截"，与需求原则相悖；方案 A 让"任何检查失败"发生在合入之前，是唯一字面满足需求的基线。
2. **风险导向**：本项目最大的 CI 风险点不是 lint，而是 better-sqlite3 的 Electron ABI 匹配（官方要求 electron-rebuild + asar unpack）与 `_electron` E2E（官方标注实验性）。两者都必须在 PR 门禁内验证，才能保证"合入即可用"。
3. **成本可行**：公共仓库使用标准 GitHub 托管 runner 完全免费，三平台矩阵零费用；唯一约束是 Free 计划 macOS 并发 5，单人开发远够用。慢反馈的代价由 concurrency 取消旧跑 + 全层缓存（npm/Electron zip）压缩到可接受。
4. **演进路径清晰**：C = A + release 工作流 + secrets 体系，M0 选 A 不损失任何东西；到发布里程碑直接叠加即可，无需返工。
