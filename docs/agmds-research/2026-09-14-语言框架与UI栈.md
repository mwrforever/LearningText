### 1.2 Electron 官方安全清单（Security Checklist，共 20 条）

来源：https://www.electronjs.org/docs/latest/tutorial/security

清单逐条要点（原文语义摘译）：

1. 只加载安全内容——应用外资源用 HTTPS（WSS/FTPS 同理）；
2. 远程内容禁开 Node 集成——自 Electron 5 起默认关闭；XSS 若能跳出渲染进程即升级为 RCE；
3. 所有渲染器开启 contextIsolation——自 Electron 12 起默认开启；仅关 nodeIntegration 不够，必须同时开隔离；关闭隔离同时会关闭沙箱；
4. 开启进程沙箱——自 Electron 20 起默认开启；勿在非沙箱进程（含主进程）加载/处理不可信内容；
5. 用 `ses.setPermissionRequestHandler()` 处理权限请求——Electron 默认自动批准所有权限请求，安全做法是默认拒绝、按来源白名单放行；
6. 禁止关闭 `webSecurity`——关闭即关闭同源策略并放开混合内容；
7. 定义受限 CSP（如 `script-src 'self'`）——优先 HTTP 头（`webRequest.onHeadersReceived`），file:// 场景用 meta 标签；
8. 禁止 `allowRunningInsecureContent`——HTTPS 页面禁加载 HTTP 脚本/CSS/插件；
9. 禁止 `experimentalFeatures`；
10. 禁止 `enableBlinkFeatures`；
11. `<webview>` 禁用 `allowpopups`；
12. 创建 `<webview>` 前校验 options/params（`will-attach-webview` 中剥离 preload、强制 nodeIntegration=false、校验 src）；
13. 限制导航——`will-navigate` 中按 URL origin 白名单 `preventDefault()`；官方提醒用 URL 解析器而非字符串前缀比较（`startsWith` 会被 `https://example.com.attacker.com` 绕过）；
14. 限制新窗口创建——`setWindowOpenHandler` 返回 `{ action: 'deny' }`，确需外开走 `shell.openExternal` 白名单；
15. 不可信内容禁用 `shell.openExternal`——可被利用执行任意命令；
16. 使用当前版本 Electron——旧版 Chromium/Node 的已知漏洞利用更泛滥；
17. 校验所有 IPC 消息的 `sender`——所有 Web Frame（含 iframe/子窗口）理论上都能发 IPC；校验 `senderFrame.origin`（用 origin 而非 URL，about:blank/blob/沙箱文档的 URL 不可信且 frame 可能为 null）；
18. 避免 `file://`，改用自定义协议——file:// 在 Electron 中权限更大，XSS 可借它读取任意本机文件；自定义协议可限定只服务特定文件集（`protocol.handle`）；
19. 检查可翻转的 fuses——`runAsNode`、`nodeCliInspect` 等可被环境变量/命令行利用，用 `@electron/fuses` 关闭；
20. 不得向不可信内容暴露 Electron API——禁暴露 `ipcRenderer.on/send/invoke` 本体，禁把回调原样透传（`IpcRendererEvent` 含 `sender` 会泄漏 ipcRenderer 实例）；每个通道写一个只取业务参数的包装函数。

### 1.3 进程模型与 preload / contextBridge

来源：https://www.electronjs.org/docs/latest/tutorial/process-model ；https://www.electronjs.org/docs/latest/tutorial/context-isolation

- 主进程：每应用唯一入口，运行在 Node 环境（可 require 一切 Node API）；职责为窗口管理（BrowserWindow/webContents）、应用生命周期（app 模块）、原生 API（菜单/对话框/托盘等）。
- 渲染进程：每个窗口一个，只负责"渲染 web 内容"，行为遵循 web 标准；**没有 `require` 与 Node API**，要在渲染端用 npm 包必须走打包器（webpack/vite 等）。历史上曾可开 Node 环境，已因安全原因默认禁用。
- preload 脚本：在 web 内容加载前、于渲染进程中运行，拥有更多权限（可访问 Node API）；contextIsolation 默认开启后，preload 与页面不共享 `window`——`window.myAPI = ...` 在渲染端是 `undefined`，必须用 `contextBridge.exposeInMainWorld`。
- utility process：主进程可用 UtilityProcess API 派生 Node 子进程，适合承载"不可信服务、CPU 密集任务、易崩组件"；比 child_process.fork 的优势是可与渲染进程建立 MessagePort 通道。
- 官方提供 TypeScript 子路径类型别名：`electron/main`、`electron/renderer`、`electron/common`，仅影响类型检查，可用来在编译期拦截"渲染端 import 主进程模块"一类错误。
- contextIsolation 官方 TS 实践：preload 暴露的 API 用 `interface.d.ts` 的 `declare global { interface Window { ... } }` 扩展，渲染端即获得类型。
- contextIsolation 官方反例与正例：`exposeInMainWorld('myAPI', { send: ipcRenderer.send })` 是坏代码（未过滤参数、放行任意 IPC）；正确做法是每条 IPC 消息一个方法（`loadPreferences: () => ipcRenderer.invoke('load-prefs')`）。

### 1.4 IPC 模式、序列化与错误处理

来源：https://www.electronjs.org/docs/latest/tutorial/ipc

- 四种官方模式：渲染→主单向 `ipcRenderer.send`/`ipcMain.on`；渲染→主双向 `ipcRenderer.invoke`/`ipcMain.handle`（Electron 7+，官方推荐）；主→渲染 `webContents.send`（无 invoke 等价物，回复走渲染端再 send）；渲染↔渲染无直接通道，须经主进程中转或主进程分发 MessagePort。
- 遗留方式官方明示避免：`sendSync` 会**同步阻塞渲染进程**直到回复，官方以性能理由建议规避；`send + event.reply` 旧双向模式需要手动配对请求/响应，仅在历史文档中保留。
- 错误处理（官方"A word on error handling"）：`ipcMain.handle` 抛出的异常**不透明**——序列化后渲染端只拿到原错误的 `message` 属性（详见 electron#24427）。含义：跨进程错误必须显式建模为返回值（Result DTO + 错误码），不能依赖异常透传。
- 通道命名：官方示例用 `dialog:openFile` 的冒号前缀并注明"前缀对代码无影响，仅作命名空间提升可读性"。
- 序列化：IPC 用 HTML 标准 Structured Clone Algorithm，只有可克隆类型能过桥；DOM 对象（Element/Location/DOMMatrix）、C++ 支撑的 Node 对象（process.env、部分 Stream）、C++ 支撑的 Electron 对象（WebContents/BrowserWindow/WebFrame）均不可序列化。
- 安全警示（三处示例反复出现）：不直接暴露 `ipcRenderer.send/invoke/on` 本体；`on` 的回调不可原样透传（会经 `event.sender` 泄漏 ipcRenderer），须包装为 `(_event, value) => callback(value)`。

### 1.5 TypeScript strict 家族与类型实践

来源：

- tsconfig reference（strict、noUncheckedIndexedAccess 等条目）：https://www.typescriptlang.org/tsconfig/
- strict 选项原文（TypeScript-Website 文档源）：https://github.com/microsoft/TypeScript-Website/blob/master/packages/tsconfig-reference/copy/en/options/strict.md
- noUncheckedIndexedAccess 选项原文：https://github.com/microsoft/TypeScript-Website/blob/master/packages/tsconfig-reference/copy/en/options/noUncheckedIndexedAccess.md
- Handbook - Everyday Types（strictNullChecks、any、type vs interface、断言）：https://www.typescriptlang.org/docs/handbook/2/everyday-types.html
- Handbook - Narrowing（收窄与可辨识联合、never 穷举）：https://www.typescriptlang.org/docs/handbook/2/narrowing.html

要点：

- `strict: true` 等价开启全部 strict 家族（strictNullChecks、noImplicitAny、strictFunctionTypes、strictBindCallApply、strictPropertyInitialization、noImplicitThis、useUnknownInCatchVariables、alwaysStrict）；官方原文："enables a wide range of type checking behavior that results in stronger guarantees of program correctness"，且未来版本可能在该 flag 下继续加严。
- strictNullChecks：官方原文"不做这些检查往往是 bug 的主要来源，我们始终建议开启"；非空断言 `!` 不做任何运行时检查，只在确信安全时使用。
- any 与 noImplicitAny：any 完全关闭类型检查，官方明示"通常应避免，用 noImplicitAny 把隐式 any 标记为错误"；any 的官方定位是"不想为某一行写长类型的临时手段"。
- noUncheckedIndexedAccess：官方语义为"经索引签名访问未声明字段时类型追加 undefined"（如 `env.NODE_ENV` 变为 `string | undefined`）。
- 可辨识联合是官方唯一推荐的"多形态数据"编码：可选属性 + 单一 interface 的写法在 strictNullChecks 下报 possibly undefined、需要非空断言、代码移动后易错；拆成多个 interface + 公共字面量判别字段（`kind: 'circle' | 'square'`）后"无论 strictNullChecks 开关与否都能正确检查"。官方点名该编码适用于"网络消息协议、状态管理 mutation 编码等任何消息方案"。
- never 穷举检查：switch default 分支把值赋给 never，新增联合成员而漏处理时立即编译报错。
- type vs interface：官方关键区别是"interface 可重开扩展（声明合并），type 不可"；官方选择启发式："use interface until you need features from type"（默认 interface，需要联合/元组/映射/原始类型别名时用 type）。别名不产生品牌效应（`type ID = string` 后仍可赋任意 string）。
- 类型断言 `as`：编译期移除、无任何运行时检查；只允许向更具体或更宽泛的方向转换，不可能的强转直接报错；确需复杂转换才用双重断言。
- 类型收窄手段全集：typeof、truthiness、相等性（`!= null` 同时排除 null 与 undefined，官方推荐写法）、in、instanceof、赋值、控制流分析、类型谓词（`x is Fish`）。

### 1.6 React 组件与状态习语

来源：

- Keeping Components Pure：https://react.dev/learn/keeping-components-pure
- Thinking in React：https://react.dev/learn/thinking-in-react
- Managing State：https://react.dev/learn/managing-state
- Sharing State Between Components：https://react.dev/learn/sharing-state-between-components
- Rendering Lists（keys）：https://react.dev/learn/rendering-lists

要点：

- 组件必须是纯函数：不修改渲染前已存在的对象/变量（props、state、context、模块级全局），相同输入返回相同 JSX；渲染中"新建"的对象允许局部修改；副作用首选事件处理器，`useEffect` 是最后手段；StrictMode 开发态双调用暴露不纯组件。
- 数组可变性规则（官方表格）：`push/pop/reverse/sort` 会改原数组，state 中禁用；`slice/filter/map` 与展开语法创建新数组。
- 最小 state 集（DRY/单一数据源）：三问判定——不随时间变化、由 props 传入、可由现有 state/props 计算得出者，都不是 state（如过滤结果、fullName）。
- state 位置：找出所有使用该 state 的组件 → 最近公共父组件 → 放置或上移；每个状态有唯一"所有者"组件。
- 受控组件：`value` 来自 props/state 且无 `onChange` 会渲染只读字段并告警；React 的"双向"是显式的"数据下行 + 回调上行"。
- 状态结构：合并同变状态；互斥状态用单一 status 而非多个布尔；避免深度嵌套。
- keys：兄弟间唯一且稳定；必须来自数据（数据库 ID / 创建时生成的 UUID），禁止渲染时生成（`Math.random()` 会导致每次渲染全量重建并丢失输入状态）；索引作 key 仅在"列表永不重排"时可接受；key 不会作为 prop 传入组件，组件需要 ID 须另传 prop；Fragment 传 key 用显式 `<Fragment key=...>`。

### 1.7 Vite 环境变量、静态资源与构建

来源：

- Env Variables and Modes：https://vite.dev/guide/env-and-mode
- Static Asset Handling：https://vite.dev/guide/assets
- Production Build：https://vite.dev/guide/build

要点：

- 暴露规则：仅 `VITE_` 前缀变量（可用 `envPrefix` 自定义）经构建期静态替换暴露给客户端源码；未加前缀（如 `DB_PASSWORD`）在客户端为 undefined。
- 官方敏感值警告（原文）："VITE_* variables should not contain sensitive information such as API keys"，这些值会被打进产物；`*.local` 文件必须 gitignore。
- 文件优先级：已存在的进程环境变量最高；`.env.[mode]` 高于 `.env`；`.local` 变体按 git 约定忽略。
- NODE_ENV 与 mode 是两个独立概念，可独立组合（`NODE_ENV=development vite build` 时 mode 仍为 production）；自定义环境用 `--mode staging` + `.env.staging`。
- TS 类型：在 `src/vite-env.d.ts` 扩展 `ImportMetaEnv` 接口获得自定义变量类型（注意该文件含 import 会失效）。
- 静态资源：JS/CSS 中 import 的资源进构建资源图、获得哈希文件名、小于 assetsInlineLimit 内联为 data URL；`public/` 目录不经处理、按根绝对路径引用、保留原名，适用于"源码中从不 import 的资源"；官方建议优先 import 方式。
- 构建：产物依赖原生 ESM（dynamic import、import.meta）；默认 target 为 Baseline Widely Available（Vite 8 默认基线：Chrome/Edge >= 111、Firefox >= 114、Safari >= 16.4），默认只做语法转换不做 polyfill；`build.target` 最低 es2015；Vite 8 底层为 Rolldown（配置键 `build.rolldownOptions`）。对本项目（Electron 自带固定 Chromium）无 legacy 需求。

### 1.8 CodeMirror 6 架构与语言包

来源：

- System Guide：https://codemirror.net/docs/guide/
- @codemirror/lang-html（官方语言包用法）：https://www.npmjs.com/package/@codemirror/lang-html

要点：

- 模块化包结构：核心三包 `@codemirror/state`（状态与变更的数据结构）、`@codemirror/view`（显示与 DOM 同步）、`@codemirror/commands`（命令与键位）；行号槽/撤销历史等都是扩展，需显式加入配置；`codemirror` 元包提供 `basicSetup` 基线（唯语言包除外，需另装）。
- 全部以 ES6 模块分发，必须配打包器或模块加载器（官方点名 Vite 为推荐）。
- 函数式核心、命令式外壳：文档与状态数据结构严格不可变，操作是纯函数；直接改属性"不被支持且多半会坏"（官方示例标注 BAD WRONG NO GOOD CODE）；TS 接口用 readonly 明示这一约束；"除非文档明确说明，对库创建对象的属性重新赋值不受支持"。
- 状态更新仿 Redux/Elm：变更先构造 transaction（纯），再 `view.dispatch` 提交；彻底换文档应新建 EditorState 而非用 transaction（避免撤销历史等残留）。
- 扩展系统：扩展值可嵌套数组、配置期自动去重；扩展习语是"导出一个返回 extension 的函数"，即使暂无参数也做成函数，便于日后加配置不破坏兼容。
- 命令签名 `(view: EditorView) => boolean`，返回 false 表示不适用、链上继续尝试；纯 state 命令用 `StateCommand` 便于不建 view 即可测试。
- 视图只渲染视口（viewport），视口外位置不可查坐标；用 `destroy` 释放视图资源；不要手工改它管理的 DOM（会被立刻还原），改观感用 decorations。
- 语言包习语：`npm i @codemirror/lang-html` 后 `import {html} from "@codemirror/lang-html"`，把 `html()` 放进 extensions 数组；`html()` 返回 LanguageSupport，内嵌 `<script>`/`<style>` 的 JS/CSS 解析支持，可配 matchClosingTags/selfClosingTags/autoCloseTags/extraTags 等。
