## 0. 选型总原则

1. **硬约束优先**："渲染样式与浏览器展示完全一致"是硬约束，只有**内嵌固定版本 Chromium 内核**的方案满足，其他一切让步于此；
2. 简单优先：不引入推测性设计，能用一个进程/一个库解决的不拆分；
3. 主流与可持续：优先社区活跃、文档充分、AI 辅助编码友好的技术；
4. 类型安全贯穿：主进程与渲染进程共享类型定义，IPC 契约编译期可查。

## 1. 关键决策点

### D1 桌面框架（最关键决策）

| 方案 | 渲染一致性 | 跨平台 | 生态/语言 | 包体 | 结论 |
| ---- | ---------- | ------ | ---------- | ---- | ---- |
| **Electron** | ✅ 自带固定版本 Chromium，三平台渲染结果逐像素一致 | ✅ Win/macOS/Linux | Node.js/TS，生态最成熟 | 大（约 80–100MB 安装包） | **✅ 选用** |
| Tauri | ❌ 使用系统 WebView（Win 为 WebView2、macOS 为 WKWebView、Linux 为 WebKitGTK），同一份 HTML 在不同系统上渲染存在差异 | ✅ | Rust + 前端 | 小（约 5–10MB） | ❌ 违反硬约束 |
| NW.js | ✅ 同为 Chromium | ✅ | Node.js/TS | 大 | ❌ 社区活跃度明显低于 Electron，无补偿性优势 |
| CEF（Chromium Embedded） | ✅ | ✅ | C++ 为主，TS 生态需大量胶水 | 大 | ❌ 开发成本最高，单人/小团队不现实 |

**结论：Electron。** 理由：需求中的"完全一致"只能靠自带内核保证；Electron 的渲染进程就是 Chromium，预览即浏览器效果，M4 模块因此不需要任何自研排版工作。代价是包体与内存占用，对桌面工具可接受。Tauri 的小包体优势在本项目不构成切换理由。

版本策略：跟随 Electron 当前稳定大版本，`package.json` 锁定精确小版本；大版本升级走独立 PR 并跑全量测试。

### D2 开发语言

**TypeScript（全栈，strict 模式）。** 主进程、渲染进程、共享 IPC 契约统一使用 TS；在 `src/shared/` 下维护类型化 IPC 通道定义，编译期拦截前后端契约漂移。

### D3 UI 框架与构建

**React + Vite。**

| 备选 | 结论 | 理由 |
| ---- | ---- | ---- |
| React | ✅ 选用 | 生态最大、组件方案（含虚拟列表、拖拽树）现成 |
| Vue | 备选 | 同样可行，无硬性优势差异，默认 React |
| Svelte | ❌ | 生态较小，树形控件等需自研较多 |

### D4 代码编辑器

| 方案 | 结论 | 理由 |
| ---- | ---- | ---- |
| **CodeMirror 6** | ✅ 选用 | 模块化、体积小、性能好，HTML/CSS/JS 语法支持开箱即用，适合嵌入双栏布局 |
| Monaco | ❌ | 体积大、启动慢，是 IDE 级需求（如完整 IntelliSense）才有必要 |

### D5 SQLite 驱动

| 方案 | 结论 | 理由 |
| ---- | ---- | ---- |
| **better-sqlite3** | ✅ 选用 | 同步 API 适合主进程串行事务模型；性能最好；默认编译包含 FTS5 与 trigram 分词器；配合 electron-rebuild 处理 ABI |
| node:sqlite（Node 内置） | 备选 | 零原生依赖是优势，但随 Electron 内置 Node 版本波动，功能与稳定性待验证，作为后续可切换项 |
| sql.js（WASM） | ❌ | 纯 JS 方便但性能差、无 WAL、需手动持久化，不适合核心存储 |

使用位置：**仅在主进程**访问数据库（单连接 + 串行化事务），渲染进程一律经 IPC。

### D6 搜索方案

**SQLite FTS5 + trigram 分词器。**

- trigram 按三字符滑窗建索引，天然支持**子串模糊匹配**与中日韩文本（按字符切分，无需分词器）；
- 文件名与文本内容进同一张 FTS5 虚表（独立列），一次查询同时命中两类结果；
- 少于 3 字符的短查询回退 `LIKE` 扫描（数据量为本地单库，可接受）；
- 拼音模糊检索（P2）：用 pinyin-pro 生成拼音列并纳入索引，不引入外部搜索引擎。

**明确不引入**：MeiliSearch、Elasticsearch 等独立搜索服务——本地单用户场景下属于过度设计，且破坏"单文件数据库即全部数据"的目标。

### D7 预览渲染管线（M4 的实现机制）

```text
编辑器保存 ─→ IPC 写入 VFS ─→ 主进程通知预览 ─→ 沙箱 iframe 重载
                                                  │ 资源请求
                                                  ▼
                                    protocol.handle('vfs://') ─→ 从 SQLite BLOB 流式响应
```

- **自定义协议 `vfs://`**：主进程注册协议处理器，把 `vfs://local/<虚拟路径>` 映射到数据库 BLOB，带正确 `Content-Type`（2026-09-18 勘误：固定 host `local`——原空 host 形态在 Blink 导航链路不可达，Task 8 E2E 探针实证）；HTML 内的相对路径引用（`./style.css`、`images/a.png`）由 Chromium 按标准 URL 解析规则自动落到同一 VFS 子树，无需改写 HTML；
- **沙箱 iframe**：预览页运行在 `sandbox` iframe 中，与编辑器 DOM 隔离，无 Node、无真实文件系统访问；比独立 `WebContentsView` 更简单，且滚动同步可用 `postMessage` 直接通信；
- **刷新策略**：编辑去抖（默认 300ms，可配置）后通知刷新；纯 CSS 变更可做局部热替换（P1 优化项）。

### D8 进程模型与 IPC

- 主进程：SQLite、VFS、搜索、导入导出、备份、`vfs://` 协议（Node 侧）；
- 渲染进程：全部 UI + 编辑器 + 预览 iframe，`contextIsolation: true` + `sandbox: true`，通过 `contextBridge` 暴露的类型化 API 调用主进程；
- 所有 IPC 通道在 `src/shared/ipc.ts` 定义常量与类型，主进程集中注册处理器并做参数校验（zod）。

### D9 打包与分发

| 方案 | 结论 | 理由 |
| ---- | ---- | ---- |
| **electron-builder** | ✅ 选用 | NSIS/DMG/AppImage 一套配置三平台产物，自动更新对接简单 |
| electron-forge | 备选 | 官方维护，但安装器定制能力弱于 electron-builder |

平台目标：Windows 10+（NSIS x64）、macOS 12+（DMG 通用包）、Ubuntu 22.04+/主流 glibc 发行版（AppImage x64）。macOS 签名公证与 Windows 签名：P2，需证书（见 01 号文档待确认问题 3）。

### D10 测试体系

| 层次 | 工具 | 覆盖对象 |
| ---- | ---- | -------- |
| 单元测试 | Vitest | VFS 树操作与事务、搜索索引一致性、路径解析、导入导出路径改写（核心逻辑 100% 覆盖） |
| 集成测试 | Vitest（真实临时 SQLite 文件） | VFS ↔ SQLite ↔ FTS5 全链路、迁移升级 |
| E2E | Playwright（`_electron` 驱动） | 新建→编辑→实时预览→搜索→删除还原主链路，三平台 CI 跑 Windows/Linux（macOS 尽力而为） |

依据全局规范：核心链路（VFS 数据一致性、状态变更、对外接口）测试 100%，非核心 ≥ 80%；测试与实现同一次提交。

### D11 代码质量与 CI/CD

- ESLint（typescript-eslint）+ Prettier + EditorConfig；
- husky + lint-staged：pre-commit 跑 lint + 格式化 + 相关测试；
- GitHub Actions：三平台矩阵，`lint → typecheck → test → build` 全绿才允许合入主干，失败自动阻断（对应全局规范第六节）；
- Conventional Commits + 版本号由 release-please 类工具管理（P1 引入）。

## 2. 技术栈清单（结论汇总）

| 层 | 选型 |
| ---- | ---- |
| 桌面框架 | Electron（最新稳定大版本，锁定小版本） |
| 语言 | TypeScript（strict） |
| UI | React + Vite |
| 编辑器 | CodeMirror 6 |
| 存储 | better-sqlite3（主进程独占，WAL + FTS5 trigram） |
| 校验 | zod（IPC 参数校验） |
| 打包 | electron-builder |
| 单元/集成测试 | Vitest |
| E2E | Playwright |
| 质量 | ESLint + Prettier + husky + GitHub Actions |

## 3. 明确不采用的技术与原因（防止后续摇摆）

- **Tauri**：系统 WebView 渲染不一致，违反核心需求（D1）；
- **独立搜索引擎服务**：本地单用户场景过度设计（D6）;
- **自研 HTML 解析/排版**：Chromium 即内核，自研必然破坏"与浏览器一致"（D7）；
- **ORM（如 Prisma/TypeORM）**：单库、表少、以 SQL 原语（事务/FTS5/BLOB）为核心的项目，ORM 反而增加抽象成本，直接使用 better-sqlite3 + 手写迁移 SQL。
